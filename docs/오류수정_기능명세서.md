# 오류 수정 기능 명세서 v0.1

- 대상 화면: 오류 수정 (담당: 본인)
- 참고: `docs/오류상세_기능명세서.md` §3의 `PUT /api/issues/{id}`(본문 필드 일괄 수정)를 이 화면이
  확장해서 쓴다. 이 문서는 수정 화면 전용으로 추가되는 부분(첨부 추가/삭제)만 다룬다.

## 1. 화면 렌더링

| Method | Path | 설명 |
|---|---|---|
| GET | `/issues/{id}/edit` | 기존 값이 채워진 수정 폼 렌더링(뷰 컨트롤러, `/api` 접두사 없음). 담당자 select는 없음(이 화면 범위 아님). 기존 첨부 목록도 함께 조회해 모델에 담는다 — 구현: `IssueViewController.editForm()`, `WEB-INF/views/issue/edit.jsp` |
| POST | `/issues/{id}/edit` | 브라우저 폼 제출(Post-Redirect-Get) — `IssueViewController.update()`. 성공 시 `redirect:/issues/{id}`, 충돌 시 `redirect:/issues/{id}?conflict=true` |

## 2. 수정 처리 (`POST /issues/{id}/edit`)

`multipart/form-data`로 전송한다(신규 첨부파일을 필드와 함께 한 번에 보내기 위함).

### 2.1 요청 항목

- `IssueSaveRequestDTO`의 본문 필드 전부(제목~개선방향, 심각도, 우선순위) — 등록 폼과 동일한 이름
- `files` / `expectedResultFiles` / `actualResultFiles` — 신규 첨부(등록 폼과 동일, `List<MultipartFile>`, 선택)
- `attachmentIdsToDelete` — 화면에서 "삭제" 표시한 기존 첨부 id 목록(복수, 선택, 없으면 빈 리스트)
- `expectedUpdatedAtRaw` — 진입 시점의 `issues.updated_at` 원본 문자열(hidden). **`@RequestParam String`으로
  받아 `LocalDateTime.parse()`로 직접 파싱한다** — `IssueViewController`의 담당자/상태변경 등 기존
  폼 액션과 동일한 이유(마이크로초 자릿수가 값마다 달라 Spring 기본 컨버터가 400을 냄, 상세 기능명세서
  참고). `IssueSaveRequestDTO.expectedUpdatedAt`(LocalDateTime 타입)에는 이 뷰 컨트롤러에서 절대
  바인딩하지 않고, 컨트롤러가 파싱한 값을 서비스 호출 시 별도 인자로 넘긴다.
  **실제 구현 중 발견**: 처음엔 이 필드도 `expectedUpdatedAt`이라는 이름으로 뒀었는데, 같은 요청에
  `IssueSaveRequestDTO request`(커맨드 객체)도 파라미터로 있어서 스프링이 그 요청 파라미터를
  `request.expectedUpdatedAt`(LocalDateTime)에도 자동으로 바인딩하려고 시도해 마이크로초 정밀도
  문자열 파싱에 실패, `@RequestParam` 값과 무관하게 컨트롤러 진입 전에 400이 났다(BindingResult
  파라미터가 없어 스프링이 바인딩 실패를 바로 400으로 반환). 폼 필드 이름을 `expectedUpdatedAtRaw`로
  바꿔 커맨드 객체 프로퍼티명과 겹치지 않게 해서 해결 - 오류 등록/JSON API처럼 커맨드 객체에
  `expectedUpdatedAt` 프로퍼티가 없거나 그 이름의 폼 필드가 별도로 없는 화면에서는 발생하지 않는
  문제라 이 화면에서만 이름을 다르게 둔다.

### 2.2 처리 순서 (하나의 트랜잭션)

1. `issues` UPDATE — `WHERE id=#{id} AND updated_at=#{expectedUpdatedAt}`. 영향받은 행이 0이면
   `IssueConflictException` → 이후 단계(첨부 추가/삭제) 전부 실행하지 않고 그대로 충돌 처리
2. 실제로 값이 바뀐 필드만 `issue_histories`에 `field_changed`로 기록(기존 `updateIssueFields` 로직 재사용)
3. `attachmentIdsToDelete`에 있는 각 첨부: 해당 이슈 소속인지 확인 → 실제 파일 삭제(`attachmentStorageService`) →
   `issue_attachments` 행 삭제 → `issue_histories`에 `event_type='attachment_removed'` 기록(2번과 같은
   `change_group_id`로 묶어서 "한 번의 수정 저장"임을 표현)
4. `files`/`expectedResultFiles`/`actualResultFiles`에 있는 각 신규 파일: mimetype 검증 → 저장 →
   `issue_attachments` insert(해당 `context`) → `issue_histories`에 `event_type='attachment_added'` 기록
   (등록 시점과 달리 **여기서는 이력을 남긴다** — 오류등록_기능명세서.md에서 "이력 기록 버전은 기존
   오류에 첨부 추가하는 향후 기능용으로 남겨둠"이라고 적어둔 게 바로 이 케이스)
5. 3~4단계에서 바뀐 게 하나도 없으면(필드도 안 바뀌고 첨부 변경도 없으면) 이력을 남기지 않는다 —
   등록과 달리 수정은 "아무것도 안 바뀐 저장"이 있을 수 있음(예: 취소하려다 실수로 그냥 제출)

파일 삭제/저장 순서는 오류등록_기능명세서.md 2.1과 동일 원칙 — 디스크 작업을 먼저 하고 성공한 것만 DB에 반영.

### 2.3 `issue_histories.event_type` 추가

`created` / `field_changed` / `attachment_added` / `comment_added`에 **`attachment_removed`** 추가.
표시 문구: "{actor}님이 첨부파일을 삭제했습니다"(오류상세_기능명세서.md 4.4 표에 추가).

## 3. 유효성 검사

- 오류등록_기능명세서.md §3과 동일(전 필드 선택, `location_url` 스킴 느슨한 확인, 첨부 mimetype 화이트리스트)
- `attachmentIdsToDelete`의 각 id가 실제로 해당 `issue_id` 소속이 아니면 조용히 무시(다른 이슈의 첨부를
  실수로/악의적으로 지정해도 영향 없음 — 400 대신 무시로 처리해 UX 단순화)

## 4. 서비스 시그니처 변경

```java
// IssueService (기존 updateIssueFields 확장)
void updateIssueFields(Long id, IssueSaveRequestDTO request,
        List<MultipartFile> files, List<MultipartFile> expectedResultFiles, List<MultipartFile> actualResultFiles,
        List<Long> attachmentIdsToDelete, LocalDateTime expectedUpdatedAt, Long actorId) throws IOException;
```

JSON API(`PUT /api/issues/{id}`, `IssueController.updateFields`)는 지금처럼 첨부 관련 인자를 전부
빈 리스트/null로 넘겨서 그대로 쓴다(기존 동작 변화 없음, `IssueSaveRequestDTO.expectedUpdatedAt`은
JSON 바디에서 Jackson이 그대로 역직렬화하므로 이 경로는 String 우회가 필요 없음).

## 5. 참고

- `issue_attachments` 테이블/컬럼 변경 없음(`context` 컬럼은 이미 있음, PR #10)
- 첨부 삭제는 이번 범위에서 "오류 수정 화면을 통한 삭제"만 지원 — 상세 화면에서 첨부를 바로 삭제하는
  버튼은 만들지 않는다(수정 화면 진입을 거치도록 통일)
