# 오류 등록 기능 명세서 v0.1

- 대상 화면: 오류 등록 (담당: 본인)
- 참고: `docs/오류상세_기능명세서.md` §3(API 설계)에 정의된 `POST /api/projects/{projectId}/issues`를 이 화면이 그대로 사용한다. 이 문서는 등록 화면 전용으로 추가되는 부분만 다룬다.

## 1. 화면 렌더링

| Method | Path | 설명 |
|---|---|---|
| GET | `/projects/{projectId}/issues/new` | 빈 등록 폼 렌더링(뷰 컨트롤러, `/api` 접두사 없음). 담당자 select 구성을 위해 사용자 목록(`id`, `displayName`)을 함께 조회해 모델에 담는다 |

## 2. 등록 처리 (`POST /api/projects/{projectId}/issues`)

`multipart/form-data`로 전송한다(첨부파일을 폼 필드와 함께 한 번에 보내기 위함).

### 2.1 처리 순서 (하나의 트랜잭션)

1. `issues` insert — 폼에 있는 값만 채우고 나머지는 컬럼 기본값(`status`/`severity`/`priority`) 또는 NULL. `project_id`=경로값, `created_by`=`updated_by`=로그인 사용자, `issue_number`는 채번 규칙(2.2)에 따라 생성
2. `issue_histories`에 `event_type='created'` 1건 기록 — 이번 등록 요청 전체의 `change_group_id`를 여기서 하나 발급해서 이후 첨부 이력에도 재사용한다
3. 첨부파일이 있으면 파일 수만큼 반복: 서버가 mimetype 검증 → `storage_key` 생성 → 디스크 저장 → `issue_attachments` insert → `issue_histories`에 `event_type='attachment_added'`, `related_record_id`=방금 만든 첨부 id, 같은 `change_group_id`로 기록
4. 성공 응답으로 생성된 `issue_id` 반환 → 프론트는 `GET /issues/{id}`로 리다이렉트

파일 저장(1번) 이후 DB insert(2~3번)가 실패하면, 이미 디스크에 쓴 파일은 정리(삭제)한다 — 반대로 DB가 먼저 커밋되고 파일 저장에 실패하는 경우가 없도록 **파일을 먼저 디스크에 쓰고 성공한 것만 DB에 기록**하는 순서를 지킨다.

### 2.2 `issue_number` 채번

서비스 전체에서 고유한 정수(프로젝트 무관 전역 시퀀스). **구현 확정(2026-09-11)**: `issues.id`(내부 PK,
`GENERATED ALWAYS AS IDENTITY`)와 `issue_number`를 동일한 값으로 취급한다 — INSERT 직후
`UPDATE issues SET issue_number = id WHERE id = #{id}` 한 번으로 맞춘다(`IssueMapper.syncIssueNumber`).
별도 채번 로직·카운터 테이블 불필요.

## 3. 유효성 검사

- 모든 본문 필드 **필수 아님** — 서버는 필수값 검증을 하지 않는다(빈 바디로도 200)
- `location_url`: 값이 있으면 `http(s)://`로 시작하는지만 느슨하게 확인, 형식이 틀려도 저장 자체는 막지 않고 화면에서 링크로 렌더링만 안 함(활성 링크 대신 일반 텍스트로 표시)
- `severity`/`priority`: 지정된 코드값 목록 밖의 값이 오면 400 (프론트 select라 정상 경로에서는 발생하지 않음)
- `assigneeId`: 숫자가 아니거나 존재하지 않는 사용자면 400
- 첨부파일: 이미지 mimetype 화이트리스트(png/jpg/jpeg/gif/webp) 외 형식은 400. 파일당 크기 제한은 임시로 10MB로 두되, 실사용 중 조정 가능하도록 설정값으로 분리한다(하드코딩 금지)

## 4. 참고

- 첨부파일 mimetype 강제 저장 규칙은 `docs/오류상세_기능명세서.md` §4.6과 동일하게 적용한다(확장자가 아니라 서버 검증 mimetype 기준으로 저장)
- 등록 폼과 상세 화면의 "본문 수정" API(`PUT /issues/{id}`)는 필드 구성이 같으므로, DTO(`IssueSaveRequestDTO` 등)를 등록/수정 공통으로 쓸 수 있다(구현 시 참고)
