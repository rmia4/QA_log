# 트러블슈팅 가이드

로컬에서 `mvn tomcat7:run`으로 QA로그를 띄워 쓰다가 문제가 생겼을 때, Claude를 부르기 전에
직접 확인·해결할 수 있는 것들을 정리한 문서. 실제로 이 프로젝트에서 겪었던 사례를 기준으로 썼다.

## 1. 서버 자체가 안 켜질 때

### 1-1. "No plugin found for prefix 'tomcat7'"
가장 흔한 원인은 **엉뚱한 폴더에서 명령어를 실행**한 것. `mvn tomcat7:run`은 반드시
`pom.xml`이 있는 `QA_log` 폴더 안에서 실행해야 한다.

```bash
cd "C:\Users\본인계정\Desktop\NC이슈노트\QA_log"
mvn tomcat7:run
```

터미널 프롬프트에 지금 어느 폴더인지 나오니(`PS C:\...\어떤폴더>`), 실행 전에 한 번 확인하는 습관을
들이면 좋다.

### 1-2. "Address already in use" / "Failed to start component"
포트 8080을 이미 다른 프로세스가 쓰고 있는 것 - 십중팔구 **자기 자신이 이전에 띄운 서버를
안 끄고 또 띄운 경우**다. Ctrl+C로 안 꺼졌거나 터미널 창을 그냥 닫아버리면 프로세스가
백그라운드에 남는다.

PowerShell에서 확인:
```powershell
Get-NetTCPConnection -LocalPort 8080 -State Listen | Select-Object OwningProcess
Get-Process -Id <위에서_나온_번호>
```
Java 프로세스가 맞으면:
```powershell
Stop-Process -Id <번호> -Force
```
그 후 다시 `mvn tomcat7:run`.

### 1-3. "BUILD FAILURE" + `[ERROR] ... .java:[줄:칸] ...` 형태의 에러 다수
**컴파일 자체가 안 되는 것** - 서버 설정 문제가 아니라 코드에 문법 오류가 있다는 뜻. 이 상태면
서버는 절대 못 뜬다. 흔한 원인:

- **git 병합 충돌 마커가 안 지워짐** - 실제로 겪은 사고(2026-09-14). 파일 안에
  `<<<<<<< HEAD`, `=======`, `>>>>>>> origin/main` 같은 줄이 그대로 남아있으면 컴파일이
  깨진다. 확인 방법:
  ```bash
  grep -rn "^<<<<<<<\|^=======$\|^>>>>>>>" src/
  ```
  (Windows PowerShell이면 `Select-String -Pattern "^<<<<<<<|^=======$|^>>>>>>>" -Path src\ -Recurse`)
  결과가 나오면 그 파일을 열어서 충돌 부분을 직접 정리해야 한다 - 어느 쪽 코드를 남길지
  애매하면 Claude에게 그 파일 경로를 알려주고 물어보는 게 안전하다(코드 로직이 얽혀있어서
  섣불리 한쪽만 지우면 기능이 사라질 수 있음).
- 최근에 `git pull`/`git merge`를 했다면 그 직후 생겼을 가능성이 높다.

## 2. 서버는 떴는데 화면에서 500/400/404 에러가 날 때

### 2-1. 지금 QA로그는 에러 화면을 예쁘게 가려준다
"500 오류입니다" 같은 화면이 뜨는 건 **정상적인 동작**이다(2026-09-14부터 적용) - Tomcat이
스택 트레이스를 그대로 보여주던 걸 막아놓은 것. 하지만 이 화면만 보고는 진짜 원인을 알 수
없다 - **진짜 원인은 서버를 실행 중인 터미널 콘솔에 그대로 출력된다.**

500/400 에러가 나면:
1. `mvn tomcat7:run`을 실행해둔 그 터미널 창으로 가서 스크롤을 올려본다
2. `[ERROR]`로 시작하거나 `Exception`이 포함된 긴 텍스트 블록을 찾는다(보통 방금 그 에러를
   낸 시점 근처에 있음)
3. 맨 위 줄(예: `java.nio.file.NoSuchFileException: ...`, `NullPointerException`,
   `PSQLException: ...`)이 실제 원인이다 - 이 한 줄만 있어도 Claude에게 훨씬 빨리 물어볼 수 있다

콘솔이 너무 길어서 못 찾겠으면, 다음번엔 아예 로그를 파일로 저장해두고 실행하면 나중에
찾기 쉽다:
```bash
mvn tomcat7:run > server.log 2>&1
```
(다른 터미널 탭에서 `type server.log`(cmd) 또는 `Get-Content server.log -Tail 100`(PowerShell)으로 확인)

### 2-2. 흔한 원인 3가지 (실제로 이 프로젝트에서 있었던 것)

| 콘솔에 이런 게 보이면 | 원인 | 직접 확인할 수 있는 것 |
|---|---|---|
| `NoSuchFileException` (첨부파일 관련) | 첨부파일이 실제로 디스크에 없음(DB 기록만 있고 파일이 없는 "고아" 데이터) | `db.properties`의 `attachment.storage.path` 경로를 탐색기로 직접 열어서 해당 이슈 번호 폴더 안에 파일이 있는지 확인 |
| `NullPointerException` | 대부분 로그인 세션이 만료됐거나, 데이터가 예상과 다른 경우 | 일단 로그아웃 후 재로그인, 그래도 나면 어느 화면/버튼에서 났는지 기록해서 Claude에게 전달 |
| `PSQLException` / `Communications link failure` | Supabase DB 연결 문제(네트워크, 비밀번호 만료 등) | `db.properties`의 `jdbc.url`/`jdbc.password`가 최신인지 확인, 인터넷 연결 확인 |

## 3. 화면이 예전 그대로 안 바뀔 때

- **JSP 파일**(`.jsp`) 수정은 서버 재시작 없이 바로 반영된다(새로고침만 하면 됨)
- **자바 파일**(`.java`) 수정은 **반드시 서버 재시작**(`Ctrl+C` 후 `mvn tomcat7:run` 재실행)해야
  반영된다 - 이걸 깜빡하고 "왜 고쳤는데 그대로지" 하는 경우가 많다
- 그래도 안 바뀌면 브라우저 캐시 문제일 수 있음 - `Ctrl+Shift+R`(강력 새로고침)

## 4. Git 관련

### 4-1. 커밋/푸시 전에 항상
```bash
git branch --show-current
git status
```
이 저장소는 여러 명이 같이 쓰다 보니 **의도치 않게 다른 브랜치로 바뀌어 있는 경우가 자주
있었다**(GUI 툴 사용, 이전 작업 잔재 등). 뭘 하기 전에 지금 브랜치가 맞는지부터 확인하는 습관을
들이면 실수를 많이 줄일 수 있다.

### 4-2. `git pull`/병합 후 이상하면
```bash
git status
```
`both modified:` 같은 표시가 있으면 병합 충돌이 아직 안 끝난 것 - 그 상태로 커밋하면 안 되고,
파일을 열어서 `<<<<<<<` 마커를 직접 정리한 뒤 `git add` → `git commit`으로 마무리해야 한다.

## 5. 그래도 안 풀리면 Claude에게 물어볼 때 이렇게

아래 4가지만 같이 알려주면 훨씬 빨리 진단된다:
1. **어떤 화면/버튼에서 났는지** (예: "오류 상세 페이지에서 담당자 변경 누르니까")
2. **터미널 콘솔에 뜬 에러 메시지 첫 줄**(위 2-1 참고, `Exception`으로 시작하는 줄)
3. **직전에 무엇을 했는지**(코드 수정, git pull, 서버 재시작 등)
4. **지금 브랜치**(`git branch --show-current` 결과)

이 정보 없이 "500 떠요"만 말하면, 콘솔 로그를 다시 뽑아내는 과정부터 다시 해야 해서 시간이
더 걸린다.
