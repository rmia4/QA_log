# 오류 상세 기능 명세서 v0.1

- 대상 화면/도메인: 오류 상세 — `issues` / `issue_comments` / `issue_histories` / `issue_attachments` (담당: 본인)
- 대상 파일(예정): `egovframework.issue.*` (controller/service/service.impl/mapper/vo/dto), `issues.xml`
- 참고: `ddl/schema.sql`, `docs/오류상세_화면명세서.md`

## 1. 개요

오류 상세 화면 하나에서 조회·등록·수정·상태변경·댓글·이력 확인까지 처리한다. 변경은 전부
`issue_histories`에 자동 기록된다(사용자가 직접 이력을 남기지 않음). 조회는 로그인한 누구나 가능하고 댓글 작성은 해당 프로젝트 담당자만 가능하다.
내용 수정·상태변경·종료·재오픈·담당자 재지정은 **오류 등록자, 현재 처리 담당자 또는 해당 프로젝트 담당자**가
할 수 있다(2026-09-14 팀 결정, 7절 참고) - 원래는 "모든 참가자가 모든 오류를 변경 가능"이었으나,
등록자가 아닌 사람이 담당자도 모르는 오류를 마음대로 고치는 걸 막기 위해 변경함.

## 2. 데이터 모델 요약

`ddl/schema.sql`이 기준. 이 문서에서는 API 설계에 필요한 범위만 재정리한다.

- `issues.status` 기본값 `new`, `severity`/`priority` 기본값 `unspecified`
- `issues`의 재현 정보 필드(`location`, `location_url`, `steps_to_reproduce`, `expected_result`, `actual_result`, `test_version`, `test_environment`, `suggested_fix`)는 전부 선택 입력 — 등록 API에 필수값 검증을 두지 않는다
- `issue_histories.event_type` ∈ {`created`, `field_changed`, `attachment_added`, `attachment_removed`, `comment_added`}(`attachment_removed`는 오류수정_기능명세서.md 2.3에서 추가)
- 한 번의 저장 요청으로 여러 필드가 바뀌면 같은 `change_group_id`(UUID 또는 타임스탬프 기반)로 여러 행을 남긴다

## 3. API 설계

공통: 모든 API는 로그인 세션이 필요하다. 조회는 전원 가능하고 댓글 작성은 해당 프로젝트 담당자만 가능하다. 그 외 쓰기 API는 오류 등록자, 현재 처리 담당자 또는 해당 프로젝트 담당자만 가능하다(7절 권한 규칙 참고).

| Method | Path | 설명 | 비고 |
|---|---|---|---|
| GET | `/api/issues/{id}` | 상세 조회(헤더+메타바+본문 전부) | 담당자명·등록자명 JOIN 포함 |
| POST | `/api/projects/{projectId}/issues` | 오류 등록 | 필수값 없음, 등록과 동시에 `event_type=created` 이력 1건 |
| PUT | `/api/issues/{id}` | 본문 필드 일괄 수정 | 3.2 참고 |
| PUT | `/api/issues/{id}/assignee` | 담당자 변경 | `field_name='assignee_id'` 이력 1건 |
| PUT | `/api/issues/{id}/status` | 상태 변경(확인 중/수정 중 전환) | `field_name='status'` 이력 1건 |
| POST | `/api/issues/{id}/close` | 종료 | status→`closed`, `closed_by`/`closed_at` 기록 + 이력 |
| POST | `/api/issues/{id}/reopen` | 다시 열기 | status→`new`, `closed_by`/`closed_at`→NULL + 이력 |
| GET | `/api/issues/{id}/histories` | 변경 이력 목록(시간순) | `comment_added` 이벤트 제외하고 반환 |
| GET | `/api/issues/{id}/comments` | 댓글 목록(시간순) | 작성자명 JOIN 포함 |
| POST | `/api/issues/{id}/comments` | 댓글 작성 | 빈 댓글 저장 금지(3.5) |
| POST | `/api/issues/{id}/attachments` | 첨부 업로드(미구현 — 등록 시 일괄 업로드만 지원, 4.6 참고) | 스크린샷 이미지 형식 제한, mimetype 화이트리스트 |

JSON API는 전부 `/api` 접두사를 쓴다. 접두사 없는 `/issues/{id}`, `/projects/{projectId}/issues/new` 등은
화면(JSP)을 반환하는 별도 뷰 컨트롤러(`IssueViewController`) 경로다 — 오류상세_화면명세서.md 참고.

## 4. 비즈니스 규칙

### 4.1 등록 (`POST /projects/{projectId}/issues`)

- 모든 본문 필드 선택 입력. 빈 요청 바디만으로도 저장 가능(자동값: `issue_number` 채번, `project_id`=경로값, `status`/`severity`/`priority` 기본값, `created_by`=로그인 사용자, `created_at`/`updated_at`=현재시각)
- 저장과 동시에 `issue_histories`에 `event_type='created'` 1건 기록 (actor = created_by)

### 4.2 본문 필드 수정 (`PUT /issues/{id}`)

- 요청에 포함된 필드 중 실제로 값이 바뀐 것만 골라 `issue_histories`에 `field_changed` 행으로 남긴다(안 바뀐 필드는 이력에 남기지 않음)
- 여러 필드가 동시에 바뀌면 하나의 `change_group_id`로 묶는다 (예: 제목+심각도 동시 수정 → 2행, 같은 group_id)
- `updated_by`/`updated_at` 갱신

### 4.3 담당자 변경 / 상태 변경 / 종료 / 재오픈

- 넷 다 내부적으로 "필드 하나 변경 + 이력 기록"이라는 동일 패턴 → 서비스 계층에 공통 메서드(`recordFieldChange(issueId, fieldName, oldValue, newValue, actorId)`)를 두고 각 API가 이를 호출하는 방식으로 구현한다
- 종료: `status='closed'`, `closed_by`=로그인 사용자, `closed_at`=현재시각 — 상태 변경 이력 1건 + (`closed_by`/`closed_at`은 부가 정보라 별도 이력 행을 만들지 않고 `field_changed(status)` 행의 컨텍스트로 취급)
- 재오픈: `status='new'`, `closed_by`/`closed_at`→NULL. 과거 종료 정보(이전 이력 행)는 그대로 보존
- 이미 종료된 오류의 본문을 수정해도 `closed_at`은 건드리지 않는다(요구사항 확정 사항)
- 재검증 필수 단계나 별도 검증자 필드는 없음 — 본인이 수정한 오류를 본인이 종료해도 무방

### 4.4 변경 이력 표시 규칙 (`GET /issues/{id}/histories`)

`event_type`별 화면 표시 문구 조립 규칙(서비스 또는 프론트에서 처리):

| event_type | 표시 규칙 |
|---|---|
| `created` | "{actor}님이 오류를 등록했습니다" |
| `field_changed` | "{actor}님이 {필드 한글명}을 {old} → {new}로 변경" — `field_name`→한글 라벨 매핑 필요(예: `status`→상태, `assignee_id`→담당자) |
| `attachment_added` | "{actor}님이 스크린샷 N개를 첨부했습니다" (`related_record_id`로 `issue_attachments` 조회) |
| `attachment_removed` | "{actor}님이 첨부파일을 삭제했습니다" (오류수정_기능명세서.md 2.3) |

`comment_added`는 이 목록 API 응답에서 제외한다(댓글 탭에서만 노출, 화면명세서 2.4 참고).

### 4.5 댓글 (`POST /issues/{id}/comments`)

- 공백만 있는 내용은 저장하지 않음(트림 후 빈 문자열이면 400)
- 저장 시 `issue_histories`에 `event_type='comment_added'`, `related_record_id`=생성된 댓글 id로 감사 기록만 남기고 화면 이력 탭에는 노출하지 않음
- 댓글 수정·삭제는 이번 범위에 없음
- **댓글 첨부(2026-09-14 추가)**: `multipart/form-data`로 `files`(선택, 이미지 형식만)를 같이 보낼 수 있다.
  `issue_attachments.comment_id`에 방금 만든 댓글 id를 채워서 저장 - 오류 본문 첨부(`comment_id IS NULL`)와
  같은 테이블을 쓰되 `comment_id` 유무로 구분한다. 첨부 mimetype 검증·저장 규칙은 4.6과 동일. 댓글
  첨부도 댓글 자체처럼 별도 이력을 남기지 않는다(감사 기록에 묻어가는 `comment_added` 하나로 충분).

### 4.6 첨부파일 (`POST /issues/{id}/attachments`)

- 첫 버전은 스크린샷용 이미지 형식으로 제한
- 저장 파일 확장자는 클라이언트가 보낸 파일명이 아니라 **서버가 검증한 mimetype 기준**으로 강제한다 — `image/svg+xml`처럼 스크립트를 담을 수 있는 형식이 확장자만 속여 저장되는 것을 막기 위함 (참고: `reference_project_mng.md`에 기록된 실사용 XSS 사례와 동일 대응)
- 업로드 성공 시 `issue_histories`에 `event_type='attachment_added'` 기록

## 5. 동시성 제어

- 낙관적 잠금: 조회 시점의 `updated_at`을 화면(hidden 필드 등)에 들고 있다가, 저장 요청에 같이 실어 보낸다
- `UPDATE issues SET ... WHERE id=#{id} AND updated_at=#{expectedUpdatedAt}` 형태로 실행하고, 영향받은 행 수가 0이면 "다른 사람이 먼저 수정함" 충돌로 판단해 409 응답
- 충돌 시 화면 UX(자동 새로고침 vs 사용자에게 확인 요청)는 아직 미정 — 구현 단계에서 별도 결정

## 6. 트랜잭션 경계

"본문 수정/상태 변경/담당자 변경/종료/재오픈/댓글/첨부" 각각은 **"본 테이블 변경 + `issue_histories` insert"가 하나의 트랜잭션**이어야 한다 — 이력 기록이 실패하면 본 변경도 롤백한다(`@Transactional` 서비스 메서드 단위로 묶는다).

## 7. 권한 규칙(2026-09-14 결정)

원래는 "역할 고정 없음, 모든 참가자가 모든 오류를 변경 가능"이었으나, 등록자·담당자와 무관한 사람이
오류 내용을 마음대로 고치거나 종료해버릴 수 있다는 문제로 아래와 같이 좁혔다.

| 동작 | 허용 대상 |
|---|---|
| 조회 | 로그인한 전원 |
| 댓글 작성 | 해당 오류가 속한 프로젝트의 담당자 |
| 본문 수정(`PUT/POST .../edit`), 상태·심각도·우선순위 변경, 종료, 재오픈 | 오류 등록자(`created_by`), 현재 처리 담당자(`assignee_id`) 또는 해당 프로젝트 담당자 |
| 담당자 재지정(`.../assignee`) | 기본은 위와 동일(등록자, 현재 담당자 또는 프로젝트 담당자). **예외**: 담당자가 아직 없는(`assignee_id IS NULL`) 오류는 누구나 자기 자신을 담당자로 지정 가능 |

**예외 규칙의 이유**: 등록자와 담당자가 둘 다 자리를 비우면(휴가/퇴사 등) 그 오류를 아무도 못 고치는
상태로 영원히 막히는 문제가 있어서, 최소한 "아직 담당자가 없는 새 오류"만큼은 누구든 자원해서 맡을
수 있게 열어뒀다. 이미 담당자가 배정된 오류까지 이 예외가 적용되진 않는다(그 경우는 등록자/현재
담당자만 재지정 가능) — 등록자·담당자가 둘 다 없는 극단적 상황(둘 다 퇴사 등)은 이번 범위에서는
해결하지 못하는 한계로 남겨둔다(관리자 역할 도입 등은 별도 검토 필요, `users` 테이블에 아직 역할
컬럼이 없음).

구현: `IssueServiceImpl.requireManagePermission()` / `requireAssigneeChangePermission()`에서 `project_assignees`도 확인한다. 위반 시
`IssueForbiddenException`(403) - 브라우저 화면(`IssueViewController`)에서는 `/issues/{id}?forbidden=true`로
리다이렉트해 안내 배너를 띄우고, 권한 없는 사용자에게는 관련 버튼/폼 자체를 렌더링하지 않는다
(`canManage`/`canClaimAssignee` 모델 속성).
